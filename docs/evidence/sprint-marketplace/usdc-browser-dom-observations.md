# Medición DOM de zoom y cargas, pendiente de ejecución

Las funciones de `scripts/usdc-browser-dom-observations.mjs` se prepararon para el evaluador DOM de sólo lectura documentado por CUA. No lanzan fetch, no registran interceptores ni observadores, no cambian CSS, no leen storage, no exportan texto privado ni valores de inputs. El operador debe usar el mecanismo de evaluación que permita su superficie; este archivo no habilita APIs de navegador adicionales.

**Zoom.** Un `font-size` calculado idéntico antes y después no descarta zoom: las unidades CSS pueden conservar su valor mientras aumenta su tamaño físico. En el mismo panel, monitor y viewport, enfocar la página y establecer una base de 100 % mediante el control real del navegador. Guardar `readUsdcZoomMetrics()` antes de ampliar. Enviar Control+Equal con el formato de teclas admitido por CUA, leer nuevamente las métricas y repetir sólo hasta observar el objetivo. A 200 % relativo a la base se esperan DPR ×2, ancho y alto CSS aproximadamente ÷2, `innerWidth × DPR` e `innerHeight × DPR` constantes y `visualViewport.scale` alrededor de 1. Un DPR constante con un viewport menor no prueba zoom; una escala visual ×2 es compatible con pinch y no con la prueba prevista de zoom de página.

`assessUsdcPageZoom(base, ampliado, {baseline100Verified:true})` exige esa combinación con tolerancia de 2,5 %. La bandera debe reflejar una base 100 % comprobada por el operador; ponerla a true no la comprueba. Si el atajo no modifica esas métricas, registrar el control como pendiente. No concluir que faltó zoom sólo a partir del font-size. Restaurar 100 % con el control real y comprobar recuperación de las métricas. Hacer esta prueba en escritorio antes de cambiar a 390 × 844; separar zoom de emulación móvil y conservar capturas sanitizadas con foco y desbordamiento.

**Cargas.** Ejecutar `readUsdcPerformanceLoads(origenPreviewExacto)` tras estabilizar cada recuperación y tras su única actualización de marketplace, antes de navegar al siguiente documento. Devuelve observaciones de navigation/resource con rutas sin query ni fragmento, tiempos relativos, timeOrigin, transferSize, encodedBodySize y decodedBodySize. Las rutas desconocidas o de otro origen se redactan. No imprimir `entry.name`, `location.href`, headers ni valores de acceso. Una carga inicial debe observar las cinco API esperadas y una actualización las dos nuevas; las dos identidades suman una previsión de 14 API. Los recursos HTML/static/RSC u otros se registran aparte.

Conservar cada observación y deduplicar snapshots sólo por documento (`timeOrigin`), índice y comienzo de la entrada; nunca agrupar peticiones distintas porque compartan ruta. `transferSize=0` puede significar caché o visibilidad limitada y no acredita cero tráfico. encodedBodySize sirve para contrastar el cuerpo comprimido; decodedBodySize no representa tráfico en red. Performance Timing no proporciona headers de solicitud, el UUID de `X-Bazaar-Acceptance-Request-Id`, todas las redirecciones cross-origin ni una captura completa de red. El buffer puede llenarse o haber sido limpiado. Por eso la función devuelve siempre `completeNetworkCapture:false`.

Conciliar las 14 API reales, sus Redis/bytes y SSR con IDs únicos del servidor y los registros del ejecutor, usando el intervalo del documento y las rutas para atribución. Si no se puede vincular de forma inequívoca cada observación con su UUID o faltan tamaños/transiciones de protección, registrar esa cobertura como incompleta; no fabricar requestId, responseBytes, status CONFIRMED ni `complete:true`. Los GET no llevan cuerpo de solicitud en este recorrido, pero la lectura DOM no mide sus headers. El tiempo de teclado/lectura tampoco se deduce sumando durations de recursos. Las observaciones sirven como evidencia auxiliar para completar la medición admitida por el navegador y el servidor.
